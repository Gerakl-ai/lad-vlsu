# Слой данных: статические снимки расписания

Для массового пилота и разговора с владельцем данных см.
[требования к источнику](VLSU-DATA-PILOT.md).

Документ описывает, откуда приложение берёт расписание после перехода на
статический хостинг, и почему выбрана именно такая схема.

## Ограничение, из которого всё следует

API ВлГУ (`https://abiturient-api.vlsu.ru/api`) **доступен из интернета, но
запрещает чтение с чужого домена**. Проверено двумя способами с постороннего
origin:

| Способ | Результат | Что означает |
| --- | --- | --- |
| `fetch(url)` | `Failed to fetch` | CORS-политика блокирует чтение ответа |
| `fetch(url, {mode:"no-cors"})` | `opaque`, тип ответа получен | хост доступен, сеть в порядке |

Отсюда следствие: **статическая страница не может запросить расписание из
браузера** — ни на GitHub Pages, ни где-либо ещё вне `*.vlsu.ru`. Пока данные
идут по запросу, нужен серверный посредник.

Выход — перестать запрашивать данные в момент открытия страницы. GitHub Actions
работает на сервере, и CORS на него не распространяется: он обходит API заранее
и кладёт результат в репозиторий обычными файлами.

```
API ВлГУ  ──►  GitHub Actions  ──►  ветка data  ──►  GitHub Pages  ──►  приложение
              (раз в 3 часа)       (валидные       (CDN)              (читает файлы)
                                    снимки)
```

## Что это даёт

- **Падение API ВлГУ перестаёт быть видимым.** CDN всегда отдаёт последний
  валидный снимок. Ровно этот сценарий наблюдался 18 сентября 2026: эндпоинт
  `student/GetGroupSchedule` отвечал `""` при HTTP 200, а расписание у студентов
  продолжало открываться.
- **Прозрачность без дополнительной работы.** Каждое обновление — публичный
  коммит. Историю может открыть и сверить кто угодно.
- **Предсказуемая нагрузка на ВлГУ.** Один обход раз в три часа вместо запроса
  на каждого открывшего приложение. При трёх одинаковых пустых ответах из
  разных институтов полный обход пропускается.
- **История изменений расписания.** Раз снимки лежат в git, разницу между
  вчера и сегодня можно показать пользователю: перенос пары, смена аудитории.

## Два правила, на которых держится надёжность

### 1. Плохой ответ не перезаписывает хороший снимок

ВлГУ умеет отвечать `HTTP 200` с пустым телом — это отказ, а не «занятий нет».
Такой ответ помечается как сбой upstream, попадает в `data/status.json` и **не
доходит до диска**: на месте остаётся последнее валидное расписание.

Без этого правила один сбойный обход стёр бы расписание всему университету.

### 2. Хэш считается только по стабильной части

`scheduleHash` берётся от `{ semester, schedule }`. В него намеренно **не**
входят «текущая пара» (`CurrentLesson`) и метки времени — они меняются каждые
несколько минут сами по себе.

Если бы они входили в хэш, сравнение расписаний всегда показывало бы ложную
правку. При этом `capturedAt` в файле обновляется после каждого успешного
получения, поэтому git-коммит может содержать только новые метки проверки.
Хэш не следует путать с критерием записи файла.

## Формат файлов

Всё лежит в ветке `data`, в каталоге `data/`.

| Файл | Содержимое |
| --- | --- |
| `catalog.json` | 14 институтов и все группы с формами обучения |
| `schedule/<nrec>.json` | Снимок расписания одной группы |
| `coverage.json` | Группы, для которых на CDN есть валидный снимок, и дата каждого снимка |
| `status.json` | Отчёт об обходе: что получено, что упало и почему |

При публикации Pages из этих снимков и резервных данных отдельно собираются
`data/gaps.json` и `data/quality.json`. Первый перечисляет группы без снимка.
Второй для каждого института и группы различает `preliminary` (данные ещё
сверяются), `reviewedDocument` (есть отметка проверки документа),
`otherAvailable` (снимок доступен, но ручная проверка каждой пары не заявлена)
и `missing` (снимка нет). Сумма категорий должна совпадать с числом групп
каталога. Эти отчёты не заменяют сверку предметов, подгрупп и аудиторий.

### `catalog.json`

```jsonc
{
  "schemaVersion": 3,
  "capturedAt": "2026-09-18T16:31:59.322Z",
  "instituteCount": 14,
  "groupCount": 966,
  "institutes": [
    {
      "id": "5b42fa53ec1dd1892e5ec44a3a60a896",
      "name": "Институт информационных технологий и электроники",
      "shortName": "ИИТЭ",
      "groupCount": 117,
      "groups": [
        { "nrec": "7936…", "name": "ПИ-124", "course": "3 курс", "forms": ["full-time"] }
      ]
    }
  ]
}
```

Поле `forms` — главное отличие от прежней схемы. Приложение до сих пор
запрашивало только `WFormed: 0`, поэтому заочники и очно-заочники не могли найти
свою группу вообще.

| Форма | Ключ | Групп |
| --- | --- | --- |
| Очная | `full-time` | 591 |
| Заочная | `extramural` | 258 |
| Очно-заочная | `part-time` | 117 |

Замер от 18 сентября 2026. Из 966 групп приложение показывало 591 — **375 групп
были недоступны**.

### Фактическое покрытие на 23 сентября 2026

В публичной ветке `data` на 24 сентября есть 965 групп в каталоге и один
сохранённый файл расписания (ПИ-124). Последний полный обход получил 965
пустых ответов HTTP 200 и не создал новые файлы. Браузер дополнительно хранит
расписания групп, которые уже успешно открывал на этом устройстве. Наличие
группы в каталоге **не означает**, что её пары доступны офлайн. Новая
`coverage.json` будет публиковать реальное число и даты валидных файлов.
Приложение отдельно обозначает локально сохранённую копию и снимок на CDN.

Проверка API через локальный proxy 23 сентября дала HTTP 200 с пустым телом
для ПИ-124 и ПИ-125. Такой ответ нельзя считать пустым учебным днём или
валидным снимком. До устранения сбоя upstream не следует заявлять покрытие
всего ВлГУ или запускать полный обход без согласования с ИТ-службой.

PDF `Raspisanie_IITE_ochnoe_osen_2026-2027_v4.pdf`, предоставленный для ИИТЭ,
побайтно совпал с файлом из [официального архива приказа №029/20](OFFICIAL-PDF-SOURCE.md).
Он может стать дополнительным источником только для проверенных по нему групп. Импорт должен
сохранять происхождение и период действия каждой записи, проверять группу,
подгруппу, дни, интервалы недель, тип недели, время и преподавателя. Сложные
строки и расхождения с API требуют ручной сверки до публикации снимков.

### `schedule/<nrec>.json`

```jsonc
{
  "schemaVersion": 3,
  "group": {
    "nrec": "7936…",
    "name": "ПИ-124",
    "course": "3 курс",
    "forms": ["full-time"],
    "instituteId": "5b42…",
    "instituteName": "Институт информационных технологий и электроники",
    "instituteShortName": "ИИТЭ"
  },
  "semester": 5,
  "schedule": [ /* ответ ВлГУ без изменений: n1…n7, z1…z7 по дням */ ],
  "quality": { "valid": true, "scheduleEntries": 6, "lessonDays": 6, "examEntries": 0, "warnings": [] },
  "scheduleHash": "…",
  "capturedAt": "2026-09-18T16:31:59.322Z"
}
```

Ответ ВлГУ сохраняется как есть: разбор строк занятий остаётся на клиенте, и
любой может сверить файл с оригиналом.

Перед полным обходом три группы из разных институтов проверяются одним запросом
каждая. Если все три дают известный пустой HTTP 200, обход не посылает ещё
сотни бесполезных запросов. В `status.json` тогда записываются `probeAttempted`,
`probeEmpty`, `scheduleSkipped`, `skipReason` и `coverageAvailable`;
существующие файлы расписания остаются нетронутыми. Другие типы ошибок не
открывают этот предохранитель и видны в отчёте обычного обхода.

Тип недели (числитель или знаменатель) в снимок **не** записывается: приложение
считает его само от календаря (`vlsuWeekModeForDate`), где неделя с 1 сентября —
числитель. Так старый снимок не может перевернуть неделю.

## Запуск

```bash
pnpm snapshot:catalog                      # только каталог, 42 запроса
pnpm snapshot -- --institutes 1 --groups 5 # небольшая проверка
pnpm snapshot                              # полный обход
```

Полезные флаги: `--out <dir>`, `--concurrency <n>`, `--delay <ms>`, `--dry-run`.

## Вежливость к API ВлГУ

966 запросов залпом с одного адреса в логах ИТ-службы неотличимы от атаки.
Поэтому обход:

- ограничивает параллельность (по умолчанию 3) и держит паузу между запросами;
- повторяет только осмысленные сбои, с экспоненциальным backoff;
- обрывает запрос по таймауту, а не висит;
- представляется честным `User-Agent` со ссылкой на репозиторий, чтобы в ВлГУ
  понимали, кто ходит, и могли связаться.

Техническая вежливость не заменяет человеческую: **до включения регулярного
обхода нужно предупредить ИТ-службу ВлГУ.**

## Известные ограничения

- Свежесть ограничена периодом обхода. «Живого» запроса из браузера не будет.
- `cron` в Actions задерживается в пиковые часы; факт задержки виден в
  `status.json`.
- История ветки `data` растёт — squash раз в семестр.
- Контракт API восстановлен из фронтенда личного кабинета, а не из документации.
  Он может измениться без предупреждения, поэтому обход обязан падать заметно.

## Как приложение читает эти файлы

`src/lib/staticData.ts` читает снимки, `src/lib/scheduleApi.ts` подключает их
первым источником. Порядок такой:

1. **Статический снимок** — `data/catalog.json` и `data/schedule/<nrec>.json`.
2. **Снимок Worker** (`/app-api/schedule/:nrec`) — только для развёртываний на
   Cloudflare, где этот маршрут существует.
3. **Прямой запрос через proxy** (`/vlsu-api/*`) — для `vite dev` и Worker.
4. **Кэш устройства** — если не сработало ничего.

На Pages-сборке в подкаталоге отсутствующий статический файл сразу означает,
что для группы пока нет опубликованного расписания: клиент не ждёт ответа от
несуществующих Worker/proxy-маршрутов. На Cloudflare и в dev они остаются
запасными путями.

Путь к данным строится от `import.meta.env.BASE_URL`: проектный сайт Pages живёт
в подкаталоге `/<repo>/`, свой домен — в корне. Базовый путь задаётся переменной
`PAGES_BASE` при сборке.

При сборке общего пакета кандидаты API и предварительного OCR сравниваются по
периоду и степени проверки. Снимок текущего семестра не заменяется снимком
прошедшего; если оба относятся к текущему семестру, непроверенный OCR не
вытесняет ответ API только потому, что его файл создан позднее. Когда
достоверный API относится к старому семестру, текущий предварительный документ
может использоваться с сохранением статуса `unreviewed`. При равном приоритете
выбирается более поздний `capturedAt`; конфликт разных расписаний с одинаковой
меткой времени останавливает сборку. Это правило закреплено тестом
`scripts/snapshot/buildUniversityBundle.test.mjs`.
Для недатированного весеннего расписания повторное получение осенью не создаёт
автоматически срок действия следующей весной: без явных границ это мог бы быть
старый ответ API. Клиент исправляет ранее сохранённые оценочные границы при
чтении локального кэша, но не меняет сроки, указанные в документе.

### Чего в снимке намеренно нет

- **Типа недели.** Числитель и знаменатель считает календарь
  (`src/lib/academicWeek.ts`), где неделя с 1 сентября — числитель. Если брать
  тип недели из снимка, старый снимок покажет студенту чужие пары.
- **Текущей пары** (`CurrentLesson`). Приложение само определяет текущее и
  следующее занятие по времени, а строка от ВлГУ меняется каждые несколько минут
  и ломала бы стабильность хэша.

### Локальная разработка

`vite dev` проксирует `/vlsu-api` напрямую к ВлГУ, поэтому статика для разработки
не обязательна. Чтобы проверить именно статический путь, положите снимки рядом с
приложением:

```bash
pnpm snapshot:catalog -- --out public/data
```

### Договор между обходом и клиентом

Обход и приложение разбирают один файл, но написаны порознь, поэтому формат
закреплён тестом `scripts/snapshot/catalogContract.test.mjs`: он берёт настоящий
собранный каталог и прогоняет его через клиентский разбор. Если форматы
разъедутся, это увидит CI, а не студент при выборе группы.

## Прозрачность: как проверить, что показано

Прозрачность здесь не заявление в README, а свойство схемы: расписание
собирается обходом в GitHub Actions, поэтому **каждое обновление — публичный
коммит**, который можно открыть и сверить.

Чтобы это было доступно не только через git, снимок несёт ссылку на себя:

```jsonc
"provenance": {
  "repository": "Gerakl-ai/vlsu-pi-124-schedule",
  "commit": "9f2c…",
  "commitUrl": "https://github.com/…/commit/9f2c…",
  "runUrl": "https://github.com/…/actions/runs/…"
}
```

Поля заполняются из переменных окружения GitHub Actions. У снимка, собранного
вручную, их нет — и это честно: такой снимок ничем не подтверждён.

В приложении это раздел **«Откуда данные»** в настройках: источник, время
снимка, его отпечаток и ссылки на коммит и журнал обхода. Свёрнут по умолчанию —
на каждый день эти сведения не нужны, но проверить можно в два нажатия.

Ссылки проверяются на схему `https` при чтении: они ведут наружу по нажатию
пользователя.

### Что видно в отчёте об обходе

`data/status.json` копит здоровье последнего прохода: сколько институтов и групп
в каталоге, сколько расписаний получено и сколько групп не ответило, с причиной.
Через месяц работы это превращается в честную картину доступности API ВлГУ —
аргумент в разговоре с ИТ-службой, основанный на замерах, а не на впечатлениях.

Группы, по которым ВлГУ не ответил, в отчёте перечислены отдельно: у них
осталось прежнее расписание, и пользователь видит это в полосе возраста данных.

### Недатированные недельные снимки

Если API прислал только номер семестра и повторяющиеся дни недели, клиент
показывает эти пары лишь в пределах соответствующего учебного полугодия:
с сентября по декабрь для нечётного семестра и с февраля по июнь для чётного.
Это защитная оценка приложения, а не опубликованный ВлГУ срок действия.
За пределами периода пользователь видит состояние «расписание не подтверждено»,
а не ложное «пар нет». Явные даты документа и датированные экзамены сохраняют
собственные границы. Для точности на стыке семестров нужен подтверждённый
источник с датами действия каждого расписания.
