# Лад ВлГУ: путь от личной PWA к пилоту

Состояние на 5 октября 2026 года. Это план развития независимого проекта, а не заявление о готовом сервисе ВлГУ. Фактические результаты аудита двух публикаций: [AUDIT-2026-09-23.md](AUDIT-2026-09-23.md). Устройство слоя данных: [DATA-PIPELINE.md](DATA-PIPELINE.md). Проверка официального архива расписаний: [OFFICIAL-PDF-SOURCE.md](OFFICIAL-PDF-SOURCE.md). Конкретный запрос к университету: [VLSU-DATA-REQUEST.md](VLSU-DATA-REQUEST.md).

## Где мы сейчас

- Работают выбор института и группы, календарь, личные события, заметки, локальный кэш и установка PWA.
- Основная публикация работает через GitHub Pages; Cloudflare Workers — параллельная публикация с отдельным pipeline, иным origin и собственными данными браузера.
- В каталоге последнего выпуска 962 группы; доступны 649 непустых снимков, для 313 групп снимка нет. Из доступных 17 имеют статус предварительных, 632 относятся к прочим доступным данным. Наличие файла не равно проверке каждой пары.
- Полный обход API 1 октября дал 632 непустых ответа и 334 пустых HTTP 200. Источник восстановился частично. Для группы ЗИСТд-126 официальный портал 2 октября показал «Расписание не найдено»; запросы `WeekType=0/1/2` вернули пустые HTTP 200. Для ПИ-124 варианты 1 и 2 в тот же день были непустыми. Нельзя трактовать пустой ответ как доказательство отсутствия занятий.
- Резервные данные из официальных документов используются для части групп, но независимая сверка содержания ещё не завершена. Для 313 групп подтверждённого актуального снимка нет; основная часть пробелов относится к заочной форме. Обход 4 октября получил 632 непустых и 330 пустых ответов. Новый официальный портал `student.vlsu.ru/schedule/institute` обращается к тому же `GetGroupSchedule`, поэтому пока не является независимым резервным источником.
- Наличие записей пользователя на одном адресе ничего не говорит об их наличии на другом. Сохранность личных данных на iPhone нельзя подтвердить из репозитория.

Текущий статус качества следует сверять с опубликованными `data/coverage.json`, `data/gaps.json`, `data/status.json` и `data/quality.json`. Отчёт качества отдельно показывает категорию проверки и положение даты относительно периода расписания. Вычисленный из номера семестра период помечен как оценка, а не как официальный срок действия. Снимок без надёжного происхождения или за пределами своего семестра нельзя выдавать за актуальный.

Локальная доработка 28.09: при недоступности резервного Worker клиент продолжает проверять другие источники вместо немедленного отказа. Старые валидные снимки Worker по-прежнему читаются первыми. В интерфейсе создание личного события доступно из календаря, а карта нагрузки на неделе свёрнута по умолчанию, чтобы занятия были видны раньше. Это не увеличило число групп с цифровым расписанием.

## Продуктовая идея

Один инструмент для любого студента: быстро узнать ближайшее занятие, открыть нужную дату, увидеть преподавателя/аудиторию и добавить личную задачу или событие. Публичное расписание и личные записи разделены. Красота интерфейса должна помогать ориентироваться, а не скрывать качество данных.

Для пилота целевой путь: выбор группы -> сегодняшние занятия -> дата/неделя -> детали пары. Дополнительные действия (заметки, темы, диагностика) остаются доступными, но не конкурируют с расписанием в первом экране.

## Архитектура и источники

```text
ВлГУ API / согласованная выгрузка / проверенный PDF
       -> ограниченный сбор и проверка качества
       -> версионированные снимки по группе и семестру
       -> открытая ветка data + GitHub Pages CDN
       -> локальный кэш устройства и PWA offline

Личные заметки и события -> только хранилище текущего origin/устройства
```

GitHub Pages подходит для статического клиента **и заранее собранных снимков**. Он не является прямым proxy к ВлГУ и не решает сбои API сам по себе. Если университет даст надёжный серверный интерфейс, можно дополнить эту схему Worker/официальным backend, не меняя модель локального первого рендера. Конкретную платформу нужно выбирать после требований ИТ-службы, а не считать Cloudflare или GitHub обязательной частью продукта.

Каждая запись снимка должна нести `source`, `sourceDocument` или endpoint, период действия, `capturedAt`, `validatedAt`, hash и качество. Пустой HTTP 200, повреждённая схема, не тот семестр, пропущенная группа или противоречие PDF/API переводят кандидата в карантин, но не заменяют последний хороший снимок. Для расписания, составленного по PDF, нужен явный статус ручной проверки и ссылка на редакцию документа. Не публиковать PDF пользователя автоматически: нужны права на распространение.

## Порядок работы

### 1. Сохранность и единый адрес

1. Выбрать один канонический origin для новой аудитории. Старые адреса не перенаправлять автоматически, пока пользователи не вывезли свои записи.
2. Проверить на реальном iPhone экспорт с прежнего ярлыка, файл резервной копии, импорт на новом origin, изображения, папки и повторный импорт с коллизиями.
3. Добавить в релизный чек-лист установку, offline reload, обновление трёх последовательных версий и восстановление после неудачной установки SW.

**Готово, когда:** есть подтверждённый перенос тестового набора записей между origin без потерь; для пользовательского iPhone результат отдельно проверен пользователем. Старый ярлык сохраняется до этой проверки.

### 2. Достоверное покрытие групп

1. Согласовать с ИТ-службой ВлГУ источник, частоту, условия доступа и контакт для исправления ошибок. Нужен не просто доступный endpoint, а гарантия смысла пустого ответа и редакций расписания.
2. Собрать fixtures реальных ответов минимум для 10 групп разных институтов, курсов, форм обучения и вариантов подгрупп. Зафиксировать контрольные даты числителя/знаменателя и экзаменационной сессии.
3. Staging PDF ИИТЭ уже извлекает изображения и координаты колонок. Добавлены черновик ревью и проверяемый локальный экспорт v3 с двумя проверяющими, ссылкой на каждую ячейку и сроком действия документа. Следующий этап - заполнить и независимо сверить пилотные группы, проверить предметы, преподавателей, аудитории и подгруппы по странице и согласовать право публикации. Не загружать непроверенные пары в production.
4. Расширить отчёт покрытия: всего групп, валидные снимки, свежие/старые, истёкший семестр, карантин, причина последнего сбоя. Показывать это и пользователю выбранной группы, и сопровождающему.
5. Настроить умеренный сбор с ограничением частоты, backoff и предохранителем от массовых пустых ответов. Опубликованный снимок заменяется только проверенным кандидатом.

**Готово, когда:** 10 пилотных групп семь дней сверены по первоисточнику; ни один пустой ответ не стёр сохранённый снимок. Массовый запуск требует отдельно измеренного покрытия, а не одного успешного теста.

### 3. Понятный интерфейс

1. Провести 5–8 наблюдаемых сессий со студентами и преподавателями. Проверить без подсказок: найти свою группу, ближайшую пару, преподавателя и расписание на дату; понять, что означает устаревший снимок.
2. Убрать повтор численности пар и конкурирующие виджеты с главного экрана. Основные команды сделать явными: группа, дата, обновление. Статус не должен выглядеть как кнопка.
3. В «Неделе» сначала дать сканируемый список дней и пар; карту нагрузки оставить вторичной. События и заметки визуально отделить от официальных занятий.
4. Сформировать строгую систему двух режимов (светлый/тёмный), ограниченное число акцентов, единые размеры иконок и зоны нажатия. Институт может давать акцент/код, группа — текстовый badge; не требуется вручную рисовать сотни иконок.
5. Переходы делать короткими и предсказуемыми. Бесконечные эффекты выключать при `prefers-reduced-motion`, в фоне и при энергосбережении. Проверить длительный нагрев/плавность на iPhone 16 Pro и среднем Android.

**Готово, когда:** новый студент находит группу и следующую пару без подсказки менее чем за 30 секунд; тестируются 393/402/430 px, landscape, VoiceOver/TalkBack и крупный текст.

### 4. Открытый пилот и сопровождение

1. Правообладатель выбирает лицензию, ответственное лицо, допустимость названия/символики ВлГУ и официальный домен. Пока этих решений нет, проект нельзя называть официальным.
2. Публикуются правила вклада, сообщения об уязвимостях, схема данных, воспроизводимая сборка, журнал изменений и процедура исправления неверной пары. Личные записи не входят в публичные отчёты и логи.
3. Пилот 5–10 групп разных институтов получает измерения: доля групп с проверенным снимком, возраст данных, успешность открытия offline/online, ошибки переключения недель, сообщения пользователей.
4. Определяются поддержка, бюджет, реакции на инциденты и план передачи инфраструктуры университету при согласии.

**Готово, когда:** владелец данных и сервиса определён, пилот подтверждён измерениями, а показ руководству явно отделяет готовые сценарии от ограничений. До этого корректно говорить «техническая beta».

## Ближайшие задачи в коде

- Согласовать с ИТ-службой выгрузку для 313 групп без снимка, в первую очередь заочных, и проверить смысл пустого HTTP 200. Запрос и контрольные примеры перечислены в [VLSU-DATA-REQUEST.md](VLSU-DATA-REQUEST.md).
- Проверить срок действия снимков, включая цифровые ответы без явных границ семестра; за пределами периода не показывать повторяющиеся пары как актуальные.
- Сделать проверяемый импорт PDF ИИТЭ в staging с контрольными примерами, затем решить, допустима ли публикация данных из документа.
- Протестировать восстановление личных записей между origin на реальном устройстве; автоматического междоменного доступа к IndexedDB нет.
- Разделить крупные `App.tsx` и стили по функциональным модулям после фиксации визуальных сценариев, чтобы облегчить QA.
- Провести мобильный UX-аудит с пользователями, затем переработать главный экран и неделю на основе наблюдений.

Не блокировать выпуск исправлений интерфейса ожиданием API, но не обещать расписание всех групп, пока у 313 групп нет подтверждённых данных, а содержание доступных снимков не прошло выборочную сверку.
